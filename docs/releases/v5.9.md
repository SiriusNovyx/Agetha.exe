# Agetha Mod v5.9: recovery prerelease

v5.9 collects the verified recovery repairs completed since v5.7.5. It remains
an experimental maintenance candidate. The GitHub release stays **draft** and
**prerelease** while review and platform acceptance remain outstanding.

This release preparation adds no features. Existing features remain present.

## Fixed in this candidate

| Area | Correction | Verification boundary |

| F03: persistence results | Targeted task/stats and related save paths report write failures instead of claiming successful saves. | Synthetic write/replace failures; this does not make all stores transactional. |

| F05: synchronous UI timeout | Pending synchronous UI work expires before later delivery. Already-started work retains its outcome instead of being falsely reported as canceled. | Deterministic fake queue and lifecycle tests; no redesign of the UI queue. |
| F02: worker/provider handoff | Failed startup withdraws pending work and releases the correct reservation; late entry and old cleanup cannot release a successor's slot. | Worker-start, reservation, and recovery-UI regressions. |

## Not fixed yet

- **Episodic-memory preservation:** malformed or unreadable
  `memory/episodic_memory.json` can appear as empty data. A later append can
  replace the damaged original. Task/stats preservation does not fix this path.
- **Conversation retention:** constructing AIEngine resets `conversation.txt`.
  It acts as a session diagnostic log, not a durable transcript. Restart does
  not reconstruct full dialogue from it; recent unsummarized turns can disappear.
- **Overlapping memory stores:** flat compatibility text, episodic JSON and the
  optional JSONL archive still have separate readers, limits and writes. No
  cross-store transaction, migration, deduplication or storage consolidation exists.
- **F11 convergence:** legacy and bounded execution mechanisms remain reachable.
  Bounded work still has engine and request state machines. Private host methods,
  compatibility branches and separate provider/speech ownership remain.
- **Lower-level subtitle/Tk boundaries:** retained subtitle drawing and clearing
  can outlive the initial request check; subtitle-worker scheduling still needs
  a separate review. The migrated request guards do not repair the whole renderer.
- **Configuration ownership:** the reload-order race is repaired, but retained
  import-time snapshots and scattered settings consumers remain. Not every
  setting applies live in every subsystem.
- **Native acceptance:** real desktop UI, audio, tray, live providers, packaged
  executables, Windows ARM/Prism and Wayland behavior have not received acceptance
  testing for this candidate. Skipped tests do not establish support or readiness.
- **Distribution size:** this phase does not establish a measured package-size
  comparison with upstream. Required dependencies, bundled assets, duplicate
  build outputs and development-only files still need a packaging audit before
  distributing a binary bundle. Larger size is not evidence of better architecture.

## Code size and architecture

The recovery work adds tests and lifetime checks. It does not establish a net
reduction in whole-project complexity.

The legacy Notepad handler grew from 28 to 53 lines. It delegates two local
lifecycle decisions to the existing owner, but adds compatibility and identity
wiring; private host access expressions increased. Two execution mechanisms
remain. The verification supports a local ownership repair and reliability
correction. Broader simplification still requires proven deletions and fewer
dependencies. No whole-project rewrite or automatic next migration belongs to
this release.

## Cautions before trying v5.9

1. Stop Agetha and make an offline backup of your entire `memory/` directory,
   `config.txt`, `.env`, and any conversation log you want to retain. Keep API
   keys private. Export a wanted transcript **before the first launch**, because
   startup resets `conversation.txt`.
2. Try a separate installation directory with disposable notes and history.
   Avoid sharing a storage directory between versions or running two instances
   against the same files.
3. Start in Compact Mode with OS command execution disabled. Enable optional
   actions only after reviewing their settings and confirmation behavior.
4. If memory data is corrupt or unreadable, stop and preserve the original bytes.
   Avoid clear/reset commands or further memory writes while investigating.
   This candidate does not recover previously lost data.
5. Use a non-critical desktop first. Keep backups of files that authorized OS
   commands can affect. Existing confirmation gates reduce risk; they do not
   make every operation harmless.
6. When reporting a problem, include the candidate commit, platform, traceback,
   and a synthetic reproduction. Remove API keys, private notes, screenshots,
   conversation text, and personal paths from public reports.

## Verification

The v5.9 candidate passed 188 focused checks and the full isolated suite:
**1,688 tests run, 1,680 passed, 8 skipped, zero failures or errors**. Every
captured run recorded zero isolation violations. All 192 project Python sources
compiled; generated command/settings references matched; the Medic script parsed.

The eight skips cover POSIX permissions, unavailable symlink privileges and
Linux/display smoke checks on this Windows test host. Most exercised desktop,
provider and audio boundaries use synthetic dependencies. Two optional diagnostic
exporters now tolerate a fresh checkout without the local audit-output directory.

Windows/Linux CI, native desktop checks and any packaged-build acceptance must
be reported separately. No pre-existing executable should be treated as a
verified v5.9 build. The draft release has no verified executable assets.

## Upgrade and rollback

The version label changes from 5.7.5 to 5.9 in the source-owned package version
and Medic surfaces. Existing data formats remain unchanged. No automated data
migration runs as part of this release preparation.

Rollback uses the previous source version and your offline backup. Keep that
backup separate from the live directory so later application writes cannot
overwrite it. A code rollback alone cannot restore truncated or overwritten data.
